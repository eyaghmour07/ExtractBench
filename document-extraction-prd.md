# ExtractBench — Product Requirements Document

## The point of this project

Everyone picks a document-extraction tool by vibes. This project replaces vibes with a measured, honest comparison: run several real extraction methods — a classical OCR engine, a modern OCR library, and a hosted vision-language model — against the same real receipts, and report field-level accuracy, latency, and cost head to head, refereed by ground truth you hand-labeled yourself.

**The interview sentence this needs to earn:** *"I benchmarked classical OCR, modern OCR, and a vision-language model on real receipts against hand-labeled ground truth, and measured exactly where each one wins and loses — on accuracy, speed, and cost."*

There's a real, specific, published claim already out there to test yourself against: a 2025 paper (Septiawan et al., *G-Tech: Jurnal Teknologi Terapan*) found GPT-4o "significantly outperforms EasyOCR" on receipt extraction. That's a concrete target — reproduce it, complicate it, or get a different result, and say so honestly either way.

## What this is NOT (read before writing any code)

- **Not a general document-processing tool.** v1 handles exactly one document type: receipts. Academic material and structured forms are real phase-2/3 additions, not v1 requirements — trying to cover all three now means building three different ground-truth schemas before anything works at all.
- **Not hardcoded to one hosted model vendor.** The vision-language model integration is a swappable interface. Gemini is the default for development (most usable free tier of the major options), but GPT-4o and Claude vision must be drop-in alternatives, not a rewrite.
- **Not a reproduction of the Septiawan et al. paper if you use a different model.** That paper's finding is specifically about GPT-4o vs. EasyOCR. If your default is Gemini, your result is its own new data point — present it as that, not as "confirming" a study that used a different model.
- **Not judged on a handful of examples.** A benchmark needs enough receipts to produce a number you'd trust, not "it got this one right."

## Hard rules — do not violate these

1. **Ground truth is hand-labeled by you, from the actual receipt image — never generated by any pipeline under test, and never trusted blindly from a dataset's own bundled labels without spot-checking a sample yourself.** Same rule as VectorSearchEngine's ground truth, for the same reason: if the referee is generated by one of the players, the benchmark measures nothing.
2. **State exactly what each number measures.** Field-level precision/recall and character error rate are different things measuring different failure modes — don't report one and imply the other.
3. **Track cost and latency per document for every pipeline, including the "free" local ones.** Tesseract and EasyOCR's cost is compute time, not zero — report it.
4. **If any pipeline scores 100% on any metric, that's a signal to check your ground truth or test set, not a result to celebrate.** Same discipline as VectorSearchEngine's "investigate suspiciously perfect recall" rule.
5. **Every dollar spent on hosted-model API calls during development should be tracked and reported**, even if it's small — "this benchmark cost $X to run" is itself a legitimate, honest data point for the cost comparison.

## Document type & data (v1)

**Receipts, sourced from SROIE** (ICDAR 2019 Robust Reading Challenge on Scanned Receipts OCR and Information Extraction) — a real, standard, publicly available dataset built for exactly this task, with ground-truth annotations for company name, date, address, and total.

**"Use your own receipts" is a designed-for feature, not an afterthought.** Build the ingestion and labeling code generically from day one — a receipt is a receipt regardless of whether it came from SROIE or your own wallet — so switching to personal documents later is a config/mode change, not a rewrite.

## Pipelines to compare (v1)

- **Tesseract** — classical OCR, local, free, decades-old baseline
- **EasyOCR** — modern deep-learning OCR, local, free, no API cost
- **A hosted vision-language model**, behind a swappable client interface — default to **Gemini** for development (verify its current free-tier limits directly before committing — this changes over time and I couldn't confirm current numbers just now), with GPT-4o and Claude vision supported as drop-in alternatives via the same interface

## Architecture

```
Receipt images (SROIE, or your own later)
    ↓
ground_truth.py    — your hand-labeled correct fields, stored once, reused by every pipeline
    ↓
pipelines/
    tesseract_pipeline.py
    easyocr_pipeline.py
    vlm_pipeline.py    — swappable client: Gemini / GPT-4o / Claude vision behind one interface
    ↓
metrics.py         — field-level precision/recall, character error rate, latency, cost per document
    ↓
Leaderboard + failure gallery (which pipeline wins on which axis, browsable examples of each one's mistakes)
```

**Module breakdown:**
- `ground_truth.py` — schema for a receipt's correct fields (merchant, date, total, line items); your hand-labeled values, stored once
- `pipelines/tesseract_pipeline.py`, `pipelines/easyocr_pipeline.py` — run the two local OCR engines, return extracted fields in the same schema as ground truth
- `pipelines/vlm_pipeline.py` — one interface, swappable backend (Gemini default); prompts the model to extract the same fields, in the same schema
- `metrics.py` — compares each pipeline's output against ground truth: field-level precision/recall, character error rate, latency, and running cost total
- `leaderboard.py` / results view — the comparison table plus a gallery of specific documents where each pipeline got it wrong, with the actual image and the actual (wrong) extraction shown side by side

## Build order

### Today: confirm the data and one pipeline work end to end

1. Download a small slice of SROIE (10-15 receipts is plenty to start)
2. Hand-label the ground truth for those receipts yourself — merchant, date, total, at minimum
3. Run Tesseract on the same receipts, compare its output to your ground truth by eye
4. Confirm the whole loop works before adding EasyOCR or the VLM

### Phase 1: all three pipelines, one metrics report

- Get Tesseract, EasyOCR, and the Gemini-backed VLM pipeline all running against the same labeled set
- Compute field-level precision/recall and character error rate for each
- **Success threshold: a real comparison table with all three pipelines' numbers, on at least 30-50 labeled receipts** — enough that the numbers mean something, not just a handful of examples

### Phase 2: make it presentable (full-stack, if you want it)

- A simple web app: upload/select receipts, trigger a benchmark run, watch results populate live
- The leaderboard and failure gallery as an actual browsable UI, not just a printed table
- This is where the "full-stack" requirement gets satisfied cleanly, and it's technically calm compared to TrajectoryLab — no exotic model-serving, no MPS/CPU discrepancy hunting, just API calls and local CPU-friendly OCR

### Phase 3: stretch goals

- Add a second document type (academic material or forms) using the same architecture, proving the design generalizes
- Add your own personal receipts as a live second dataset
- Swap in GPT-4o or Claude vision alongside Gemini and compare hosted models against each other, not just against the free local tools

## What "done" looks like for the portfolio

A README with: the comparison table (accuracy, latency, cost per pipeline), a handful of side-by-side failure examples with real images, an honest note on where your result agrees or disagrees with the Septiawan et al. finding, and — if you built the phase-2 web app — screenshots of the live leaderboard.
